## ① 세 영역과 `git add`

### 배운 것
- Git의 세 영역
  - **Working Directory**: 내가 실제로 편집하는 파일
  - **Staging (Index)**: 다음 커밋에 넣을 내용을 모아 두는 곳
  - **Repository**: 커밋으로 기록된 히스토리 (`.git`)
- `git add`는 **그 시점의 파일 내용을 Staging에 스냅샷으로 올린다**. 파일 자체를 표시해 두는 게 아니라 add한 순간의 내용이 올라감
  - add 이후에 파일을 또 고치면 Staging과 Working이 달라짐 → `git status -s`에 `AM`
  - `commit`은 Staging에 있는 것만 기록하므로 add 이후의 수정은 커밋에서 빠짐 → 커밋 후 `M`이 남음

### 실습 결과 (`three_areas.sh`)

| 단계 | `git status -s` | 의미 |
|---|---|---|
| 파일 생성 | `?? a.txt` | Working에만 있음 (untracked) |
| `git add` | `A  a.txt` | Staging에 올라감 |
| add 후 재수정 | `AM a.txt` | Staging 버전 ≠ Working 버전 |
| `commit` | ` M a.txt` | Staging분만 기록, 재수정분은 Working에 남음 |

- `git show HEAD:a.txt`는 `hello`, `cat a.txt`는 `hello world` → 커밋에는 add 시점의 내용만 들어갔음을 확인

### 명령 정리

| 명령 | 비교 대상 |
|---|---|
| `git diff` | Working vs Staging |
| `git diff --staged` | Staging vs 마지막 커밋(HEAD) |
| `git status -s` | 왼쪽 글자 = Staging 상태, 오른쪽 글자 = Working 상태 |
| `git log --oneline --graph` | 커밋 히스토리 한 줄 요약 |

## 확인 질문 답변
Q. `git add`는 정확히 무엇을 하는가?
A. add한 시점의 파일 내용을 Staging에 스냅샷으로 올린다. 커밋은 Staging에 있는 내용만 기록하므로, add 이후에 고친 부분은 다시 add하기 전까지 커밋되지 않는다.
